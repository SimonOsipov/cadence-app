(`ruleset go kmp api-integration ios`), `go test ./... -race` и

Полный гейт (`ruleset go kmp api-integration ios`) зелёный на `1f34280`.

Найдено попутно и починено: помощник `auditRows` читал entity как `invites` для
всего, кроме `account.delete`, — значит «ни одной строки `patient.create` не
осталось» считал строки не той сущности и был зелёным при любом исходе.

Измерено и оказалось не дефектом: наполовину русские заголовки снапшотов — это
заголовки самих мастеров. Снапшоты на месте не правили.

Блоки 3.4, 3.5 и 5 пройдены следом. Что в них изменилось:

- обе ветки `ErrLockUnavailable` теперь производятся кодом (вторая — через
  `lock_timeout`), и обе проверки `conn.Close` убиваются мутацией;
- `GOTRUE_RATE_LIMIT_EMAIL_SENT` меряется поведением на своём контейнере с квотой
  2: переименование переменной роняет тест;
- сборка без `onboarding` отвечает 500 на обоих маршрутах, а не разыменовывает nil;
- `classify` отвечал 409 «адрес занят» на `care_team_assignments_one_primary` и
  терял драйверную ошибку из цепочки — оба исправлены;
- `settle` больше не приглашает через безымянный `default`;
- запись об удалении аккаунта идёт на отвязанном контексте;
- у пула запросов есть `MaxConns`;
- `TestMain` во всех шести местах не теряет контейнеры при панике;
- `LookupBatch` ушёл из потребительского интерфейса, пароль в стенде больше не
  подставляется в SQL сырым, три теста перестали быть правыми по случайности.

**Оставлено сознательно, с причиной:**

- две копии `INSERT INTO app.profiles` в `writePatient`. Единственный способ
  свести их в одну — продублировать `DEFAULT` колонки `locale` в коде, а это
  ровно то, чего избегает нынешний комментарий. Дублирование дешевле;
- `LockClass` с одним значением: тип не даёт передать в замок произвольное
  число, и это дороже, чем приведение обратно к `int32` на одной строке;
- `record`: две строки, но они держат порядок двух транзакций и объяснение к нему;
- `ErrUnknownTimezone` недостижим по HTTP — таймзона приходит при первом входе,
  чего этот блок не делает. Арм покрыт таблицей отказов;
- контракт «сначала `cycle.Reset`» по-прежнему ничем не навязан: навязать его
  из текущей формы стенда нельзя, слабость названа в комментарии `Cycle`.

**Осталось и требует решения (было три, осталось две):**

1. ~~`app.invites` не пишет роль.~~ **Закрыто 17.08.2026**, ADR-011. Дефект
   воспроизведён тестом до починки и оказался тяжелее записанного: неверное завершение
   пишет пациентский профиль, после чего первый арм `ClaimFor` отвечает 409 на любой
   последующий запрос — адрес не просто израсходован, а непригоден навсегда. Миграция
   `000010` добавляет колонку роли, `NOT NULL` и **без `DEFAULT`**; `ClaimFor` сравнивает
   роль выше `hasBeenOpened`. Пять мутаций, каждая убита названным тестом.

2. Запись `account.delete` подшита под `patient_id` уничтоженного аккаунта,
   который профилем не станет никогда. Ни в чьей ленте её не видно. Варианты:
   `NULL` (акт про аккаунт, не про пациента) или перенос записи после нового
   приглашения — но тогда провалившееся приглашение теряет запись об удалении.
   Нынешнее поведение защищено собственным тестом, поэтому не менял.
3. Детали 409 — оракул существования аккаунта для любого аутентифицированного
   врача. Осознанное решение, но нигде не записанное как ADR.

## Блок 1. Ломает перед мерджем

### 1.1 Набор тестов зелёный по случайности порядка — измерено

```
go test ./internal/identity/                 → ok
go test ./internal/identity/ -shuffle=on     → FAIL, восемь подтестов
```

`httpserver.NewAPI` подменяет `huma.NewError` глобально под `sync.Once`
(`internal/platform/httpserver/api.go:111`). `answerFor`
(`internal/identity/providers_test.go:218`) требует `*huma.ErrorModel`. Тест
проходит, только пока успевает отработать раньше любого теста, который строит
API. Единственный тест в модуле, зависящий от порядка.

### 1.2 За хрупкостью — расхождение с проводом — измерено

`answerFor` смотрит объект **до** нормализации. `problemTypeFor(503)` даёт
`ProblemUnavailable` (`api.go:195`), и `normalise()`
(`platform/httpserver/problem.go:247`) затирает detail константой пакета.

- тест требует `detailBusy` = «Сейчас заняты — повторите через минуту.»
  (`providers_test.go:161`)
- вызывающий получает `unavailableDetail` = «Сервис временно недоступен.
  Повторите запрос через несколько минут.»

`detailBusy` (`create_patient.go:60`, используется на `:121`) не доходит до
клиента никогда. Восемь подтестов — единственное покрытие ответов кадрового
маршрута — меряют документ, которого нет.

**Починка:** гнать отказ через смонтированный маршрут, как делает
`onboarding_test.go:post`, и проверять `*httpserver.Problem` после маршалинга.
Затем решить судьбу `detailBusy`: удалить и передавать английскую строку для
лога (как соседняя ветка `ErrProvisionerUnavailable`), либо дать
`ProblemUnavailable` detail по причине.

### 1.3 Потерянный `remember()` навсегда сжигает адрес — прочитано

`invite()` (`onboarding.go:283`) лечит только случай, когда ошибся сам
`provisioner.Invite`. Если `Invite` **удался**, а следующий `remember()` упал по
любой причине кроме `23505`, строки в `app.invites` нет. Повторная попытка:
`Lookup` находит аккаунт → `held()` даёт `Invite:false` → `RefuseNotOurs` → **409
навсегда**, и прикладного пути назад нет (никакая роль не держит `DELETE` на
`invites`, аккаунт тоже никто не удаляет). Сам упавший запрос отвечает 500, потому
что `classify` (`patients.go:280`) знает только `23505`.

Достижимо на обоих маршрутах: `InvitePatient` через `record()`
(`onboarding.go:163`), `InviteProvider` через прямой `remember()`
(`onboarding.go:205`).

Реальные причины: исчерпание сервисного пула (`serviceMaxConns = 4`),
`statement_timeout` 5s, оборванное соединение. И детерминированная —
`invites.invited_by uuid NOT NULL REFERENCES app.profiles(user_id)` даёт `23503`,
если профиль вызывающего врача удалили, пока его токен (до часа) ещё жив.

**Починка:** повторить приём из `invite()` — при падении `remember()` после
удавшегося приглашения перезаписать на `context.WithoutCancel` + `recoveryBudget`
до возврата ошибки. И классифицировать `23503` на `invites_invited_by_fkey` как
отказ, а не как 500.

### 1.4 Оба `context.WithoutCancel` не убиваются ничем — измерено мутацией

```
lock.go:65      WithoutCancel(ctx) → ctx   → набор ЗЕЛЁНЫЙ (мутант выжил)
onboarding.go:293 WithoutCancel(ctx) → ctx → набор ЗЕЛЁНЫЙ (мутант выжил)
```

Обе строки существуют ради отказа, который ни один тест не воспроизводит.

- `lock.go`: освобождение, унаследовавшее оконченный контекст, не доходит до
  сервера, и сессионная блокировка уезжает в пул на весь срок процесса.
  `TestAFailingHolderReleasesTheLockForEverybodyElse`
  (`lock_integration_test.go:164`) работает на живом `t.Context()` — освобождение
  удаётся в обоих случаях.
- `onboarding.go`: восстановление на уже потраченном дедлайне получает
  `DeadlineExceeded`, строки нет, адрес входит в тот самый постоянный 409, ради
  которого арм и написан. `TestAnInvitationWhoseAnswerWasLostIsStillRecorded`
  (`onboarding_integration_test.go:178`) готовит потерянный ответ на живом
  контексте.

**Починка:** два теста, каждый с названной мутацией в комментарии.
Для блокировки — отменить контекст изнутри замыкания и потребовать, чтобы тот же
ключ выдался второму пулу (`twoPoolsOnOneDatabase` уже есть). Для восстановления —
провести тот же сценарий через `InvitePatient` с контекстом, чей дедлайн уже
истёк, и потребовать, чтобы строка в `app.invites` всё равно появилась.

## Блок 3. Дыры в тестах

### 3.1 Вызов `checkBody` в `InvitePatient` без свидетеля

`onboarding.go:141` стоит до блокировки и до провизионера, и комментарий
объясняет зачем: кривое тело не должно тратить адрес. Ничего это не меряет.

Единственный отказ в `checkBody`, который схема huma поймать не может, —
`ErrTwoPrimarySpecialists`: `SpecialistBody.Primary` это голый `bool` без
межполевого ограничения, так что `[{primary:true},{primary:true}]` доходит до Go.
Все быстрые тесты (`onboarding_test.go:112`) и все тела в интеграции
(`onboarding_integration_test.go:588`, `body()` ставит `primary: i == 0`) шлют
ровно один главный.

Удалить вызов `checkBody` из `InvitePatient` — набор останется зелёным, а в
проде приглашение уйдёт, строка `invites` закоммитится, и `check()` внутри
`CreatePatient` ответит 422. То есть ровно тот дефект, который закрывал
`TestNamingOneSpecialistTwiceIsTheFormsMistakeAndNothingIsSent`, на соседней
ветке никем не покрытой.

**Тест:** случай двух главных рядом с тестом про повтор специалиста — 422 **и**
`count(*) FROM app.invites WHERE email = $1 = 0` **и**
`clinic.provider.invitations() == 0`.

### 3.2 `refusalFor` пациентского маршрута без таблицы отказов

`create_patient.go:96`. У кадрового маршрута есть исчерпывающая таблица
(`providers_test.go:107`) со сторожами `notTheSentence`/`mustNotMention` против
ожиданий, выведенных из проверяемой константы. У пациентского — нет. Не покрыто:

- `ErrNotAProvider → detailNotAProvider` (`:125`) — единственный 422, которому
  спека нарочно дала свою русскую фразу (расхождение 9): идентификатор пришёл из
  списка, и перечитывание формы его не найдёт. Два теста доводят до него и
  проверяют **только статус 422**. Подменить `detailNotAProvider` на
  `detailUnprocessable` — ничего не упадёт;
- `ErrAlreadyExists → 409` (гонка мимо блокировки) — не достигается ничем;
- `default → 500` — не достигается.

### 3.3 `ProblemConflict` не проверен ничем

`httpserver/api.go:191`, `problem.go:27`. По всем `*_test.go` — ноль упоминаний.
Каждый тест на 409 разбирает документ и смотрит только `Detail`. Удалить ветку
`case http.StatusConflict` — и каждый 409 поедет с `"about:blank"`, молчаливая
поломка контракта для клиента, который ветвится по `type`. У соседей
`ProblemForbidden` и `ProblemUnavailable` свидетели есть.

### 3.4 Прочие непокрытые места

- `ErrSpecialistNamedTwice` не назван ни одной проверкой: тест
  (`onboarding_integration_test.go:829`) не отличает его от

  второй внутри транзакции (адрес потрачен);
- `ErrLockUnavailable` не производится кодом, который его производит: обе ветки
  `lock.go:45` и `:60` без покрытия; `providers_test.go:159` строит сентинел
  руками. Обе ветки с `conn.Close`, существующие ради непротекания блокировки в
  пул, для набора мертвы. Достижимо: `MaxConns = 1`, один держатель внутри,
  второй вызов с контекстом на 100 мс;
- нулевой `onboarding` (`create_patient.go:65`, `create_provider.go:58`) — никто
  не шлёт POST на такую сборку, и `mount_test.go:38` больше не «строит всю
  поверхность так, как композиционный корень»: `main.go` передаёт пять опций,
  `assembled()` — три;
- `GOTRUE_RATE_LIMIT_EMAIL_SENT` пришпилен строкой, а не поведением. Тот же
  дефект, что ветка чинила для `MAILER_MAX_FREQUENCY`: переименуют или перестанут
  читать — оба теста останутся зелёными.

### 3.5 Хрупкость

- `TestTheAdminInviteIsNotCoveredByThePerAddressGap`
  (`invitations_integration_test.go:156`) требует, чтобы два HTTP-обхода уложились

## Блок 5. Упрощения и мелочи

- `classify` (`patients.go:280`) и `classifyStaff` (`providers.go:103`) уже
