# Питание и рецепты

## Описание

Порт `mobile/src/features/meal/` и `mobile/src/features/recipe/` — пяти экранов, 4 047 строк прототипа — на Compose Multiplatform против моков. Питание отвечает на вопрос «сколько я съел против цели», рецепты — на «что съесть, чтобы закрыть остаток белка». Домен уже написан (`shared/domain/Nutrition.kt`); строится всё, что между ним и экраном: точность макросов, примитивы рисования, два репозитория, шов разбора текста и пять экранов с их точками входа.

Разбор еды остаётся моком с заготовками — настоящий LLM приходит в M9. Фоторежим и голос видны и помечены будущим: подставлять заготовку вместо результата запрещено инвариантом nutrition №5, хотя прототип именно это и делает.

## User Story

**As a** пациент на протоколе

**I want** записывать съеденное текстом и собирать блюда из рецептов клиники

**So that** я вижу остаток по калориям и белку на сегодня и знаю, чем его закрыть

## Acceptance Criteria

- [ ] Записанный приём виден на четырёх поверхностях сразу: кольца «Питания», `MealHero` и `TodayMeals` на «Сегодня», подпись в листе действий — одно хранилище, а не четыре копии
- [ ] Тост подтверждения называет сумму дня, **включающую** только что записанный приём
- [ ] Время приёма берётся из часов; в диффе фичи нет ни `08:42`, ни `13:14`
- [ ] Макросы справочника и позиций приёма хранятся с точностью 0,1 г; сумма позиций записанного приёма равна показанному «на порцию × порций», а итог дня считается точно и округляется один раз при заполнении `TodaySummary`
- [ ] Разбор текста живёт за `MealParser` и даёт три состояния: «разбираем», «разобрали», «не получилось». В последнем экран не гаснет и уже разобранные позиции остаются правимыми
- [ ] Фото и голос видимы, помечены будущим и **не** возвращают заготовленный результат
- [ ] Килокалории позиции рисуются своим числом: две позиции с разными калориями дают два разных числа
- [ ] Приём, разобранный из текста, пишется с `source = AI_TEXT`; добавленный из рецепта — с `RECIPE` и `recipeId`. `MANUAL` в этом порте пути не имеет, кроме сида, и это сказано вслух
- [ ] Неделя на «Питании» считается из посеянной истории, подписи дней выводятся из дат, последняя — «Сег»
- [ ] Дневные итоги сида одинаковы в `UTC` и в `Europe/Moscow`
- [ ] Цели приходят как `NutritionTargets` через репозиторий; константы `1800/140/200/60` существуют ровно в одном месте — в сиде целей
- [ ] Рецепт библиотеки и рецепт пациента различаются по `ownerId` и попадают в свои секции — проверено на экране, а не только в репозитории
- [ ] Сохранённый рецепт открывается сразу после сохранения, возврат из него ведёт на «Рецепты», а не в конструктор
- [ ] `RecipeDetail` различает «ещё не загружено» и «такого рецепта нет» — два разных экрана, оба с тестом
- [ ] Ни один из пяти маршрутов не остаётся `PlaceholderScreen`; `PLACEHOLDER_MEAL_NAME` удалён
- [ ] Существующие ожидания на числа сида (`840`, `2 приёма`, `Осталось 960 ккал · 80 г белка`) остаются верными либо правятся поимённо, с названием файла и строки
- [ ] `./gradlew ktlintCheck detekt testAndroidHostTest` и iOS-половина гейта зелёные

## Scope / Non-scope

**В объёме.** Пять экранов прототипа (`LogMeal`, `Nutrition`, `Recipes`, `RecipeDetail`, `RecipeBuilder`) и лист выбора ингредиента; их точки входа (`MealHero`, `TodayMeals`, `ActionChooserSheet`, карточка-переход с «Питания»); недостающие примитивы дизайн-системы; два репозитория и шов разбора; справочник ингредиентов, шесть стартовых рецептов и недельная история приёмов как сид; список последних приёмов в `TodayMeals` — записанный долг, который закрывается здесь.

**Вне объёма.** Настоящий разбор через LLM (M9, `POST /me/meals/parse-text`). Серверная персистентность приёмов и рецептов (M9). **Ручной ввод позиций** — решение предложения, раздел 6: прототип его не даёт, инвариант nutrition №4 остаётся неизмеримым до M9. Фотографии блюд: слот под фото на герое «Рецептов» рисуется (150 px, иконка камеры на linen) — сама картинка нет. Вода: `NutritionTargets.waterMl` остаётся неиспользованным, ни один экран прототипа воду не показывает. Редактирование и удаление записанного приёма — прототип этого не даёт.

## Технические детали

**Точность.** Решение предложения, раздел 4. Справочник и позиция приёма несут макросы в десятых долях грамма целым числом; `Meal.totals` остаётся точным; `Macros` остаётся целым и получает значения **одним** округлением — при заполнении `TodaySummary` и при показе.

**Репозитории** (`shared/repository/`; конвенция: `suspend`, без состояния, запись возвращает запечатанный результат — образец `DoseLogResult`, `AddVialResult`):

```kotlin
interface NutritionRepository {
    suspend fun day(date: LocalDate): NutritionDay        // приёмы, итоги, цели
    suspend fun week(endingOn: LocalDate): NutritionWeek  // семь дней: дата, ккал, белок
    suspend fun log(draft: MealDraft): MealLogResult      // Written(id, dayTotals) | Rejected
}

interface RecipeRepository {
    suspend fun library(filter: RecipeFilter): RecipeList
    suspend fun recipe(id: RecipeId): Recipe?
    suspend fun ingredients(query: String): List<Ingredient>
    suspend fun save(draft: RecipeDraft): RecipeSaveResult
}
```

`MealLogResult.Written` несёт **итоги дня после записи** — иначе тост поднимется на снимке, взятом до неё (step-13).

**Шов разбора** — `shared/parsing/MealParser.kt`, не репозиторий: это сервис, а не хранилище.

```kotlin
interface MealParser { suspend fun parse(text: String): MealParseResult }
```

`MealParseResult` — `Parsed(mealName, transcript, items)` либо `Unavailable`. `Unavailable` существует, чтобы ветку недоступности было чем пройти: совпадение по ключевым словам (`meal/data.ts:119-127`) стартует с `bestScore = -1` и потому **всегда** что-то возвращает.

**Мок и общее хранилище.** `CadenceMocks` держит `private val meals = MockSeed.meals.toMutableList()` рядом с `events` и `addedVials`; и `MockNutritionRepository`, и `MockTodayRepository` читают этот список. Механизм описан в KDoc `CadenceMocks.kt:70-73`. Видимость в UI — счётчик `reloads` (`CadenceShell.kt:114`), инкремент после каждой записи.

**Экраны берут DTO и лямбды**, репозиторий внутрь не приходит (`TodayScreen.kt:35-38`). Значит `parse(text)` и `ingredients(query)` приходят на экран `suspend`-лямбдами из оболочки — образец `onLoadMetric` (`CadenceShell.kt:250,404-425`), где различены «ещё не пришло» и «такого нет».

**Время в прототипе.** `LogMealScreen.tsx:365` пишет `'08:42'`; приём из рецепта получает `'13:14'` — `DAY_STATES.midday.now` (`meal/data.ts:165`), подставляемое в `AppState.tsx:134`. Два разных фальшивых времени в одной сессии.

**Порядок макросов.** `MealHero.kt:155-157` рисует Б/Ж/У, экраны питания — белок/углеводы/жиры. Расхождение `MealHero` уже записано в реестре (`docs/prototype-divergences.md:359-362`) вместе с переименованием ног; порт его не трогает, новые поверхности идут в порядке прототипа.

## Архитектурное решение

Порт идёт через два репозитория и отдельный шов разбора, а не через один нутриционный фасад. Разделение проходит по тому, что заменится в M9 разными эндпоинтами: приёмы и цели — `POST /me/meals` и `nutrition_targets`, рецепты и ингредиенты — `POST /me/recipes` и поиск по справочнику, разбор — `POST /me/meals/parse-text`.

Главный компромисс: приёмы живут одним изменяемым списком на `CadenceMocks`, а не внутри репозитория питания. Внутри было бы аккуратнее по инкапсуляции — и ровно так же неверно, как копия дня внутри `Today`: две открытые вкладки разошлись бы ([[a-guard-that-walks-an-empty-shell]]).

Второй компромисс — недельная история. Прототип рисует шесть дней константами и седьмой настоящим (`NutritionScreen.tsx:407-409`), потому что истории у него нет. Мы её сеем — **литералами от `DEMO_NOW`, как весь остальной сид**. Привязывать приёмы к системным часам нельзя: проект закрыл этот урок закреплением часов, а не сида (`CadenceShell.kt:104-107`), и клоко-относительные приёмы при календарных дозах дали бы мир, где пациент ест сегодня, а взвешивался год назад.

Третий: недостающие примитивы рисования выносятся в отдельный первый шаг. Числовой степпер нужен четырём местам, полоса значения против цели — трём, составная полоса вклада — двум. По правилу `ActionChooserSheet.kt:180-186` второе место вызова уже переводит примитив в дизайн-систему.

## Decomposition

### step-1: Примитивы питания в дизайн-системе

Шесть примитивов, каждый со вторым и далее местом вызова. **Холст ничего не утверждает** — это уже трижды выведено в проекте (`CadenceGauge.kt:47`, `CadenceStepper.kt:157`, `CadenceCharts.kt:126`): у каждого примитива с геометрией должна быть чистая функция расчёта либо `testTag` на измеримом боксе по образцу `usageBarTag`, и тест ставится на неё, а не на рисунок.

- `CadenceStepper(value: Double, min: Double, max: Double?, step: Double, decimals: Int)` — верхняя граница необязательна: правка граммов позиции в записи приёма её не имеет (`LogMealScreen.tsx:880`), а лист ингредиента имеет (600). Четыре места вызова здесь и ещё пять в спеке `kmp-journal-and-body`, где вес и процент жира идут шагом 0,1 — поэтому не целочисленный. Дробный шаг держать целым множителем, как уже сделано в `CadenceDoseStepper` (`CadenceStepper.kt:48`), иначе шаг 0,1 накопит ошибку. Здесь `decimals = 0` во всех четырёх местах.
- `CadenceMacroBar(label, value, goal, color)` — три места, все на «Питании» (`NutritionScreen.tsx:517-519`), цвета различны и потому параметр. Итоговая полоса записи приёма полосой **не** является — это четыре числовые колонки (`LogMealScreen.tsx:904-959`), и она рисуется своим кодом.
- `CadenceSplitBar` — составная полоса вклада по правилу 4/4/9 ккал на грамм: карточка рецепта и живая карточка конструктора.
- `CadenceRings` — два концентрических кольца (внешнее калории, внутреннее белок), текст в центре.
- `CadenceWeekBars` — семь столбцов, пунктир цели с подписью, масштаб `max(значения, цель) × 1,05`, сегодняшний столбец выделен цветом и непрозрачностью. Рассмотреть расширение существующего `CadenceUsageRow` (`CadenceGauge.kt:98`) прежде, чем заводить новый: он уже рисует семь столбцов с масштабом по максимуму.
- `CadenceSegmented` — три режима записи приёма и «На порцию / Всё» в карточке рецепта.
- `CadenceTextField` — четыре новых поля (чат, имя рецепта, шаг, поиск) против двух существующих сырых `BasicTextField` (`DoseSteps.kt:385`, `AddVialScreen.kt:125`). Четыре места — примитив заводится; два существующих переводятся на него в этом же шаге либо остаются, и это записывается.

**Тесты.** Степпер не переступает границу с обоих концов и не двигается на границе; при `max = null` растёт неограниченно — против мутации «границей ограничен только один конец». Доли колец считаются чистой функцией и проверяются на фикстуре, где **доля белка отличается от доли калорий**, — иначе тест зелёный при мутации «оба кольца считают калории» ([[a-passing-assert-may-pass-for-another-reason]]). Масштаб недельных столбцов растёт, когда значение превышает цель.
